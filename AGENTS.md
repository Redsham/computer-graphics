# Правила разработки

## Область работы и существующие модули

- Активная разработка — `semester-5/`. `semester-4/` является архивом: изменения только по явному запросу.
- Перед редактированием изучить затрагиваемый модуль, его публичные контракты, прямые зависимости,
  вызывающий код и тесты. Кратко обозначить пользователю границы изменения и способ проверки.
- Новую возможность сначала размещать в новом файле, системе, проходе или приложении лабораторной,
  подключая через существующий интерфейс и composition root. Не дописывать её в общий координатор.
- Существующие модули менять минимально. Если для задачи требуется затронуть модуль вне согласованной
  области, изменить публичный API, граф зависимостей, ABI GPU или формат сохранённых данных,
  сначала описать конкретную причину, альтернативу и влияние и уточнить расширение задачи у пользователя.
  До ответа продолжать независимый анализ и подготовку; зависимые изменения не вносить.
- Явный запрос на исправление/рефакторинг названных модулей уже разрешает необходимые изменения
  в этих границах. Не запрашивать повторное разрешение на уже согласованную работу.
- Не смешивать исправление ошибки с массовым форматированием, переносом файлов или новыми функциями.
  Сохранять совместимость API и данных; миграции проверять отдельно.

## Зависимости и расширение

- Источник разрешённых связей — `semester-5/architecture.json`; устройство — `semester-5/docs/ARCHITECTURE.md`.
- `EngineCore` не знает Metal, GPUShared, AppKit, SwiftUI и приложения. `GPUShared` содержит только C/MSL ABI.
  `EngineMetal` зависит от EngineCore/GPUShared; `EngineMac` связывает ядро, Metal и платформенный UI.
  Приложение собирает зависимости и сцену. Обратные связи и циклы между targets запрещены.
- Состояние передавать через конструкторы и типизированные контексты. Не вводить singleton,
  глобальное изменяемое состояние, service locator или ссылки из движка на Sandbox/лабораторную.
- Система реализует `EngineSystem`, проход — `RenderPass`; порядок явно задаётся при сборке приложения.
  Особенности лабораторной остаются в её приложении. Не расширять центральный switch для каждого нового типа сцены.
- У компонента, ресурса, задачи и окна должен быть понятный владелец и момент освобождения.
  `internal`/`private` — по умолчанию; `public` только для реального межмодульного контракта.
- Один файл отвечает за одну связную обязанность. Разделять координацию, алгоритмы, хранение,
  сериализацию и UI. Не создавать абстракции, не имеющие конкретного потребителя.
- Для каждого изменения повторно проверить входящие/исходящие зависимости и выполнить
  `python3 scripts/check-architecture.py`. Новые связи требуют обоснования, тестов и обновления документации.

## Производительность

- До изменения определить, затрагивается ли кадровый цикл, ECS-запросы, выделение памяти,
  синхронизация CPU/GPU, публикация UI, дисковый ввод-вывод или readback.
- Изменения горячего пути сопровождать сопоставимыми Release-замерами до/после на одинаковой сцене,
  разрешении, MSAA, оборудовании и настройках диагностики. Порядок — `semester-5/docs/PERFORMANCE.md`.
  Для переносов без изменения выполнения достаточно объяснить отсутствие влияния и проверить поведение.
- Различать CPU encoding, ожидание слота, GPU execution и интервал показа. Не называть микробенчмарк FPS.
  Указывать выборку, единицы, разброс, инструментирование и ограничения. Не заявлять ускорение без замеров.
- Не создавать pipelines и постоянные GPU-ресурсы каждый кадр. Экранные ресурсы менять при изменении
  размера/формата, изменяемые данные — только в завершённом слоте. Учитывать стоимость временных массивов,
  сортировок, подписок, копирования и хранения замороженных снимков.
- GPU readback и ожидание idle допускаются в захвате/экспорте/тестах/завершении; не переносить их
  в обычное рисование. Новую оптимизацию проверять по изображению, памяти и времени, а не только по CPU.
- UI публикует диагностику с ограниченной частотой и только при изменении данных. Смена вкладки,
  обновление статистики и перенос окна не должны сбрасывать пользовательское состояние или размеры Dock.

## Metal и компьютерная графика

- Перед изменением Metal API, шейдера или графического алгоритма читать актуальную первичную документацию:
  Apple Developer, спецификацию MSL, официальные примеры/WWDC; для алгоритмов — оригинальную публикацию
  или книгу авторов. Начальные источники и проверенные решения — `semester-5/docs/METAL_RESEARCH.md`.
- Проверять availability в установленном SDK и поддержку на реальном GPU. Зафиксированная база —
  macOS 26+, Apple Silicon, Swift 6, Metal 4. Переход на новую базу согласовать отдельно.
- В заметке к изменению записывать дату проверки, точные URL, применимое API/технику, принятое решение
  и эксперимент. Не считать дату существующей заметки подтверждением актуальности для следующей задачи.
- Metal 4: residency не заменяет синхронизацию и владение ресурсом. Сохранять ресурсы до завершения GPU,
  allocator сбрасывать только после завершения слота, hazards разрешать явными barriers/fences/events.
  Для drawable сохранять wait/signal/present. Уменьшение области барьера требует анализа зависимостей.
- Общие структуры/индексы объявлять в GPUShared. Проверять размеры, выравнивание и смещения полей;
  не дублировать структуры в Swift и MSL. Отладочные схемы обновлять вместе с ABI.
- У графической техники документировать координаты, порядок матриц, диапазон глубины, единицы,
  цветовое пространство, форматы/точность, MSAA/resolve и ограничения. Различать учебное приближение и PBR.
  Свет считать в linear RGB; исключать повторное sRGB-кодирование. Проверять граничные случаи и изображение.

## Проверки и оформление

- Код/API — английский; README и проектные пояснения — русский. Четыре пробела, 110 символов,
  пустые строки между методами и этапами, `MARK` для связных разделов, каждый SwiftUI-модификатор отдельно.
  Следовать `.swift-format`, `.clang-format`, `.editorconfig`; команды — `scripts/format-code.sh`.
- Не использовать `try!` для инициализации/выполнения движка и не скрывать ошибки. Ограниченные возможности
  диагностики могут отключаться с понятным сообщением. Swift 6 actor isolation сохранять явно.
- Проверять изменённый контракт, затем подходящие unit/GPU/UI тесты. Изменение layout проверять
  реальным перетаскиванием, минимумами, повторными обновлениями и восстановленной раскладкой;
  одного `setPosition` или успешной сборки недостаточно.
- После изменений общего движка: проверка архитектуры и формата, Debug/Release arm64 через workspace,
  тесты с Metal API Validation. SwiftPM CLI не заменяет GPU-проверку: `.metal` компилируется Xcode.
- Перед завершением просмотреть diff, проверить отсутствие изменений архива, описать изменённые
  зависимости, результат тестов/замеров и оставшиеся ограничения. Коммит/push — в рамках указаний пользователя.

Правила описывают работу при каждой задаче; они не означают запуск фонового мониторинга или автоматизаций.
