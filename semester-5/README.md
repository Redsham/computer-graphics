# 5-й семестр — Graphics Engine

Общий графический движок для лабораторных: **macOS 26+, Apple Silicon, Swift 6, Metal 4**.
`Sandbox` — отдельное демонстрационное приложение с освещённым кубом и управляемой камерой.

Инструменты отладки: [консоль, журнал, профайлер и Frame Debugger](DIAGNOSTICS.md).
Панели и настройки Renderer поддерживают dock с вкладками слева, справа и снизу,
перетаскивание в отдельные окна, изменение размеров и сохранение раскладки.

## Запуск

Откройте `GraphicsEngine.xcworkspace`, выберите схему **Sandbox**, устройство **My Mac** и нажмите Run.
Нужны Xcode 26+ и установленный компонент Metal Toolchain. Подпись настроена на Sign to Run Locally:
Apple Developer Team, генератор проекта и сторонние библиотеки не требуются.

```sh
# Из корня репозитория
xcodebuild -workspace semester-5/GraphicsEngine.xcworkspace -scheme Sandbox \
  -configuration Debug -derivedDataPath /tmp/graphics-engine-build build

MTL_DEBUG_LAYER=1 xcodebuild -workspace semester-5/GraphicsEngine.xcworkspace \
  -scheme Sandbox -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath /tmp/graphics-engine-build test

xcodebuild -workspace semester-5/GraphicsEngine.xcworkspace -scheme Sandbox \
  -configuration Release -derivedDataPath /tmp/graphics-engine-release build
```

Схема Run включает Metal API Validation. Шейдеры Swift Package компилируются Xcode в `default.metallib`
и загружаются из ресурсного bundle `EngineMetal`, а не из bundle приложения.
`swift build --package-path semester-5/Engine` проверяет Swift-модули, но CLI SwiftPM копирует `.metal`
как ресурс; **GPU-тесты и приложение нужно собирать через Xcode / xcodebuild**.
Для CPU-тестов отдельно: `swift test --package-path semester-5/Engine --filter CoreTests`.

## Организация

```text
semester-5/
├── GraphicsEngine.xcworkspace/
├── Sandbox.xcodeproj/          # Приложение, общий test target, shared scheme
├── Sandbox/                   # Сборка демосцены и комплектный JSON
└── Engine/                    # Локальный Swift Package
    ├── Sources/
    │   ├── EngineCore/        # ECS, математика, системы, снимки, конфигурация
    │   ├── EngineMetal/       # Ресурсы GPU, кадры, проходы и шейдеры
    │   ├── EngineMac/         # MTKView, ввод, окно приложения и настройки
    │   └── GPUShared/         # Общий ABI Swift/C/Metal
    └── Tests/
        ├── EngineCoreTests/
        └── EngineMetalTests/
```

Зависимости проверяются границами targets:

```text
EngineCore ← EngineMetal ← EngineMac ← Sandbox / приложения лабораторных
                 ↑
             GPUShared
```

`EngineCore` использует стандартную библиотеку, Foundation и simd. Он не импортирует Metal, AppKit
или SwiftUI. `Sandbox` создаёт сцену и регистрирует системы; движок не знает о лабораторных.
Другие графические API и платформенные оболочки в текущую версию не входят.

## Сцена и обновление систем

`World` хранит компоненты по типам. `Entity` содержит индекс и поколение: уничтоженная сущность
не становится валидной при повторном использовании индекса. Запросы возвращают сущности в порядке индексов.
`Transform`, `Camera`, `MeshRenderer`, `DirectionalLight` содержат данные; `Spin` — компонент демоанимации.
Родительская иерархия пока не вводится: `Transform` описывает положение в мировом пространстве.

`SystemScheduler` исполняет переданный массив систем последовательно. `start` вызывается перед первым
обновлением, `stop` — в обратном порядке. Повторный `stop` безопасен. В демо:

1. `EngineMac` снимает состояние ввода один раз на кадр.
2. `CameraControlSystem` обновляет позицию и ориентацию камеры.
3. `SpinSystem` обновляет вращение объектов.
4. `TransformSystem` вычисляет матрицы `WorldTransform`.
5. `RenderExtractionSystem` создаёт независимый `RenderSnapshot`.
6. После всех систем применяются отложенные структурные изменения.

При обновлении разрешено менять существующие компоненты через `World.set`.
Создание/удаление сущностей и добавление/удаление компонентов выполняйте через `World.deferMutation`.
Эти изменения видны системам со следующего кадра. Начальную сцену создавайте до запуска scheduler.
Для нового `Transform` без вычисленного `WorldTransform` извлечение использует его текущую матрицу.

Все CPU-системы, хранилища и кодирование команд изолированы `MainActor`.
В первой версии нет параллельного scheduler, физики или фиксированного шага: используется реальное
время кадра с ограничением 0,1 с после паузы. GPU исполняет команды асинхронно.

Чтобы добавить систему, реализуйте `EngineSystem` и передайте её экземпляр в нужной позиции массива
при создании `EngineSession`. Зависимости передавайте в конструктор системы. Глобального доступа к миру нет.

## Координаты и данные GPU

Правая система координат: +X вправо, +Y вверх, камера смотрит вдоль −Z.
Матрицы column-major; вектор умножается справа. Матрица объекта: `T * R * S`.
Проекция использует глубину Metal 0…1; FOV задаётся в градусах, углы камеры и анимации — в радианах.
Нормали преобразуются inverse-transpose матрицей объекта. Нулевой масштаб объекта отклоняется при загрузке кадра.

`RenderSnapshot` содержит матрицу камеры, свет и список объектов с `MeshID` / `MaterialID`.
Metal-объектов в нём нет. Материалы передаются в линейном RGB.
`GPUShared.h` — единственный источник структуры вершин, uniform-данных и индексов привязки.
C static assertions проверяют размеры: вершина 32 байта, кадр 112, объект 144.

## Проходы и GPU-ресурсы

Начальный пайплайн:

1. `ForwardPass`: непрозрачная геометрия, back-face culling, depth test, ambient + направленный свет;
   результат — `hdr` (RGBA16Float) и `depth` (Depth32Float). MSAA 4× использует отдельный multisample
   target с resolve в `hdr`.
2. `OutputPass`: читает `hdr`, применяет экспозицию и tone mapping `x / (1 + x)`, пишет `surface`
   (BGRA8 sRGB). Преобразование линейного цвета в sRGB выполняется форматом целевой текстуры.

`RenderPass` объявляет входы/выходы через `PassDeclaration`. Проверяются порядок производителей,
имена, форматы, количество samples и наличие финального `surface`. Вход не может ссылаться на
ещё не произведённую текстуру; повторная запись в то же имя запрещена — используйте новое имя результата.
Все объявленные текстуры имеют размер выходной поверхности. Автоматического render graph,
алиасинга памяти и изменения разрешения отдельных проходов в первой версии нет.

Расширение пайплайна:

- Реализуйте `declaration`, `prepare`, при необходимости `prepareFrame`, затем `encode`.
- В `prepare` создавайте pipelines через `PassPreparationContext.pipeline`. Для шейдеров лабораторной
  передавайте её `MTLLibrary` через параметр `library`; без него используется библиотека движка.
- `prepareFrame` вызывается после ожидания завершения выбранного слота. Здесь регистрируйте свои
  buffers/textures через `context.frame.useResource`, прежде чем движок выполнит `residency.commit`.
  Для изменяемых ресурсов и argument tables храните три экземпляра, выбирая по `context.frame.index`.
- В `encode` получите текстуры через `context.texture`, откройте encoder, вызовите `context.synchronize`
  **до draw/dispatch**, закодируйте команды и закройте encoder даже при ошибке. Pipelines и прочие
  объекты, которые могут заменяться, удерживайте через `context.retain` до завершения кадра.
- Передайте экземпляры проходов в `MetalRenderer(passes:)`. Координатор кадра менять не требуется.

Синхронизация между encoders сейчас консервативная: queue barrier всех стадий с device visibility.
Это явная корректная основа Metal 4; более узкие барьеры и async compute требуют отдельного профилирования.

У каждого из трёх слотов свои allocator, command buffer, argument tables, uniform/object buffers,
экранные текстуры и residency set. `MTLSharedEvent` запрещает повторное использование до завершения GPU.
При resize/MSAA слот пересоздаёт свои attachments только после завершения своего предыдущего кадра.
Другие слоты удерживают старые ресурсы. Pipeline cache различает библиотеку, функции, формат и MSAA.

`ResourceStore` создаёт меши из треугольников и материалы; `makeCube` — процедурный пример.
`removeMesh` и `removeMaterial` освобождают запись из хранилища. Сначала удалите ссылки из сцены;
выполняющиеся кадры удерживают buffers мешей до завершения. Идентификаторы не переиспользуются.
Ссылка на отсутствующий ресурс возвращает ошибку. Прямого уничтожения используемого GPU-буфера нет.

Перед завершением работы приложения вызывается `EngineSession.shutdown`: системы останавливаются,
последняя GPU-работа ожидается. После ошибки рисование приостанавливается; сообщение остаётся в панели,
кнопка Retry rendering запускает повторную попытку. Нулевой viewport и отсутствие drawable пропускаются.

## Настройки и управление

Комплектные значения находятся в `Sandbox/DefaultConfiguration.json`.
Пользовательский JSON записывается атомарно в `GraphicsEngine.Sandbox/settings.json` внутри Application Support.
Приложение использует App Sandbox, поэтому полный путь обычно находится внутри
`~/Library/Containers/com.redsham.graphics.Sandbox/Data/Library/Application Support/`.
Для каждой лабораторной задавайте отдельный `settingsName` и bundle identifier.

Диапазоны: FPS 1–240, MSAA 1/4, экспозиция 0,1–8, FOV 20–110°, скорость 0,1–20, RGB 0–1.
Повреждённый или невалидный пользовательский файл вызывает предупреждение и загрузку комплектных значений.
Кнопка Restore defaults сохраняет комплектные настройки, включая случай повреждённого файла.
Настройки применяются на границе кадров и сохраняются после успешного рендеринга.

WASD — движение, Q/E — вниз/вверх; обзор — перетаскиванием правой кнопкой мыши.
Щелчок по viewport передаёт ему клавиатурный фокус. Потеря фокуса окна/viewport сбрасывает нажатые клавиши.
Панель показывает фактический FPS, время CPU-кадра (включая ожидание ресурсов GPU) и число объектов.

## Новая лабораторная

Создайте отдельный macOS App target/проект в своём `lab-N/` и добавьте его в workspace.
Подключите локальный пакет `Engine`, продукты `EngineCore` и `EngineMac`; для собственных GPU-проходов
подключите также `EngineMetal`. Минимальная версия macOS — 26.0, Swift — 6, архитектура — arm64.

Используйте `SandboxApp` как пример точки сборки: загрузите комплектный JSON, создайте `EngineSession`,
зарегистрируйте системы, загрузите ресурсы и заполните `session.world`. Покажите `EngineView(session:)`.
Массив проходов можно передать в `EngineSession(passes:)`, сохраняя готовую оболочку и настройки.
Для собственного окна используйте `MetalRenderer` напрямую. Сам движок копировать не нужно.

## Проверки

`SandboxTests` запускает исходники из обоих каталогов тестов пакета:

- поколения сущностей, удаление компонентов, отложенные структурные изменения и порядок жизненного цикла;
- проекция 0…1, перемещение камеры, анимация и извлечение матриц, реальный шаг времени;
- проверка конфигурации, сохранение и восстановление после повреждения JSON;
- ошибочный порядок проходов, несовпадение форматов/samples, повторные выходы;
- реальный внеэкранный рендер: геометрия на фоне, перекрытие дальнего куба ближним, изменение экспозиции,
  более трёх кадров, смена MSAA/wireframe, resize, пропуск отсутствующей поверхности, удаление ресурса
  после отправки на GPU и восстановление после ссылки на удалённый меш.

GPU-тест требует Metal 4; при отсутствии совместимого устройства он явно пропускается.
Сложные эффекты, импорт моделей, редактор сцен и первая лабораторная будут добавляться отдельно.

Модель команд и синхронизации: [Metal 4 core API](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api), [Resource synchronization](https://developer.apple.com/documentation/metal/resource-synchronization).
