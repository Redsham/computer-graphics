# Анализ производительности

## Порядок работы

Перед изменением указать горячий путь, предполагаемую стоимость, владельца памяти и проверяемую
гипотезу. Сначала сохранить baseline, затем менять код. После изменений повторить те же нагрузки
в Release. Сохранять сырые результаты, версию кода и окружение; сравнивать медиану и разброс,
а не один запуск. Для GPU фиксировать сцену, размер drawable, MSAA, wireframe, число объектов,
прогрев, diagnostics/capture и включённую validation. CPU/GPU измерения проводить отдельно.

```sh
# Из корня репозитория; один прогрев, затем семь замеров каждой нагрузки
swift run -c release --package-path semester-5/Engine EngineBenchmarks /tmp/engine-benchmark.json

# Архитектура, стиль, Debug, тесты с Metal Validation, Release
./scripts/check-engine.sh
```

Benchmark target использует только EngineCore, не создаёт окно и не требует default.metallib.
Он не запускается автоматически при сборке Sandbox. Возвращаемые checksum предотвращают
удаление всей нагрузки оптимизатором; число итераций и итоговые значения записаны в JSON.

## Результаты рефакторинга 10.11.2026

Окружение: Apple M4, 10 CPU cores, macOS 26.5.2 (25F84), Xcode 26.6 (17F113), Swift 6.3.3,
arm64, `swift run -c release`. До — движок `84c3f07` с добавленным инструментом измерения;
после — реализация этого рефакторинга с тем же инструментом. Числа — время всей серии, миллисекунды.

| Нагрузка | Итераций в серии | До: медиана [min; max], ms | После: медиана [min; max], ms |
|---|---:|---:|---:|
| Запрос неизменившегося набора из 10 000 Camera | 1 000 | 6789.562 [6721.024; 7109.992] | 0.046 [0.045; 0.058] |
| Добавление FrameProfile в историю ёмкостью 300 | 100 000 | 26.931 [26.867; 27.247] | 3.273 [3.030; 3.600] |
| Spin → Transform → Extraction для 1 000 объектов | 100 | 263.522 [260.513; 392.207] | 39.208 [38.979; 39.469] |

Сырые результаты: [до](performance/2026-11-10-before.json), [после](performance/2026-11-10-after.json).
Каждый результат включает семь серий после прогрева, контрольные суммы совпадают.
Сверхмалое время cached-query измеряет повторное получение готового массива после прогрева:
это не время построения набора при изменении сцены. Structural churn нужно измерять отдельно.

Причины эффекта: кэш упорядоченных Entity ID сбрасывается только при вставке/удалении компонента
или уничтожении сущности; замена данных компонента кэш не сбрасывает. Кольцевое хранение устраняет
сдвиг элементов заполненной истории/журнала. Имена систем и проходов готовятся вне обычного кадра.
UI получает новый массив профилей только при изменении revision; выбор каналов preview выполняется
до пиксельных циклов. Последние два изменения отдельно в этой таблице не измерялись.

Ограничения: результаты локальные, без изоляции частот/фоновых процессов, без memory profiler;
это CPU microbenchmarks, не FPS и не измерение GPU-ускорения. Кэш ECS требует дополнительного
массива ID на запрошенный тип компонентов; frozen snapshots могут удерживать прежние массивы.
Материализация публичного массива истории остаётся O(n), но выполняется на границе чтения,
а не при каждом append. Сбор/поиск запоздалых GPU результатов остаётся ограниченным ёмкостью истории.

## GPU и дальнейшие гипотезы

Профайлер различает CPU систем, CPU encoding проходов, ожидание слота, GPU timestamps и residency.
Capture/trace помечены instrumented: readback и ожидание completion искажают обычную нагрузку.
Сравнивать производительность следует без capture и validation; correctness отдельно проверять с ними.
Для анализа использовать [Metal debugger](https://developer.apple.com/documentation/xcode/metal-debugger)
и [инструменты профилирования Apple](https://developer.apple.com/videos/play/wwdc2026/388/).

Текущие консервативные `.all → .all` barriers сохраняют корректность расширяемых проходов,
но могут ограничивать overlap. Сужение возможно после описания stage/access dependencies и измерения.
Depth сохраняется для debugger/контрактов; memoryless, aliasing, batching/instancing и сортировка
по material/mesh требуют отдельной нагрузки и проверки изображения. Они не включаются ради рефакторинга.
Экранная память умножается на три слота и при MSAA; оценивать allocations вместе с разрешением,
а не только числом draw calls. Отсутствие регрессии pixel/depth/exposure в тестах не доказывает GPU-ускорение.
