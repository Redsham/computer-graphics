# Границы и расширение движка

Правила для каждой задачи — [AGENTS.md](../../AGENTS.md). Разрешённый граф проверяется
[скриптом](../../scripts/check-architecture.py) по [architecture.json](../architecture.json),
манифесту SwiftPM, package dependencies Xcode-приложения и прямым импортам исходников.
Это проверка границ, а не полноценный анализ Swift AST или оценка производительности.

## Модули и владельцы

| Target | Обязанности | Зависимости проекта |
|---|---|---|
| GPUShared | Общие C/MSL типы, индексы; compile-time проверки ABI | Нет |
| EngineCore | Математика, ECS, компоненты, данные кадра, конфигурация, платформенно независимая диагностика | Нет |
| EngineMetal | GPU-контекст, ресурсы, подготовка и выполнение проходов, GPU-диагностика | EngineCore, GPUShared |
| EngineMac | MTKView, ввод, сессия, настройки, консоль, профайлер, Frame Debugger, Dock | EngineCore, EngineMetal |
| Sandbox | Сборка зависимостей и демонстрационной сцены | EngineCore, EngineMac |
| EngineBenchmarks | Отдельный CPU-бенчмарк без окна и GPU | EngineCore |

Foundation/os/simd допустимы в ядре. Metal и платформенные UI-фреймворки находятся в адаптерах.
Приложения лабораторных используют те же products, но движок не ссылается на их типы.
Targets остались прежними; добавлен только отдельный исполняемый инструмент измерений.

## Организация исходников

- `EngineCore/ECS`: World, контракт системы, контекст и scheduler; `Systems` — конкретные системы.
  `Scene`, `Input`, `Math`, `Configuration`, `Console`, `Diagnostics`, `Collections` разделяют данные и сервисы.
- `EngineMetal/Context` создаёт GPU-контекст. `Pipeline` проверяет ресурсы и готовит states;
  `Passes` содержит реализации. `Resources` владеет мешами/материалами. `Rendering` управляет
  слотами и загрузкой данных. `Diagnostics` хранит CPU-снимки и реализует readback/таймстемпы/trace.
- `EngineMac/Application` связывает ECS, renderer и представление. `Console` отдельно содержит
  parser-facing адаптер сессии, группы команд и UI. `Profiler`, `FrameDebugger`, `Settings`, `Input`
  и `Dock` отвечают за собственные интерфейсы. Работа с файлами вынесена в `SessionExports`.
- `SandboxApp` — composition root; `SandboxScene` создаёт только демонстрационные сущности и ресурсы.

Размер файла не является целью: маленькие связанные типы могут оставаться вместе.
Причина разделения — разные владельцы, жизненные циклы или причины изменения.

## Выполнение кадра и владение

`EngineSession` на MainActor снимает ввод, обновляет системы, передаёт RenderSnapshot в MetalRenderer
и публикует статистику. В компонентах и снимках нет Metal-объектов. Scheduler сохраняет порядок
регистрации; структурные изменения World применяет после завершения всех систем.

`RenderPipelinePlan` готовит проходы при изменении конфигурации, проверяет TextureContract и сохраняет
декларации/имена. `MetalRenderer` выбирает завершённый слот, вызывает подготовку, encode и submission.
`FrameResources` владеет allocator, command buffer, изменяемыми буферами, argument tables,
экранными текстурами и residency set. Изменять слот можно только после его completion event.
При resize/MSAA заменяются ресурсы только этого завершённого слота; другие слоты сохраняют свои.

`RendererInstrumentation` владеет профилями, GPU timestamps, shader log, запросами захвата и native trace.
`CaptureRecorder` выполняет readback, а CapturedFrame/Texture/Buffer — независимые Codable/Sendable данные.
Захват может ждать GPU и расходовать до 256 MiB staging-памяти; обычный кадр readback не делает.
Pass-owned ресурсы регистрируются через `prepareFrame`/`FrameResources.useResource` до submission.
Residency и сильное удержание до completion проверяются отдельно от hazards/barriers.

`DiagnosticsDock` владеет постоянными hosting views и отдельными окнами; представления монтируют
их только при совпадении владельца. Размеры контролирует NSSplitView, видимость — модель Dock.
Native drag-to-collapse отключён: он конфликтовал с восстановлением состояния модели.
Оформление вкладок, host-контейнеры, native drag source и drop targets находятся отдельно.

## Как добавить возможность

| Возможность | Где реализовать | Что подключить |
|---|---|---|
| Новая логика сцены | Новый EngineSystem рядом с системой или в приложении лабораторной | Массив systems в composition root |
| Новый GPU-этап | Новый RenderPass, шейдер и контракты входов/выходов | Массив passes; координатор не редактировать |
| Команда лабораторной | `session.commands.register` в приложении | Имя, помощь, обработчик с переданными зависимостями |
| Новый инструмент UI | Своя View и состояние; platform adapter в EngineMac | Осознанная регистрация в Dock; generic-плагинная система пока не нужна |
| Новая лабораторная | Отдельное macOS-приложение и shared scheme | Products пакета, JSON defaults, системы и сцена |

Контракт RenderPass допускает подготовку на любое изменение конфигурации. Поэтому не следует
кэшировать подготовку только по MSAA, если пользовательский проход зависит от других настроек.
PipelineCache отдельно переиспользует готовые GPU states по шейдерам, библиотеке, формату и sample count.
При частичной ошибке подготовки весь plan считается неподготовленным: повтор с прежней конфигурацией
обязан восстановить states всех проходов. Ёмкость object buffer обновляется только после успешного выделения.

## Анализ перед изменением

Для задачи записать: потребитель → изменяемый контракт → зависимости → владелец состояния → место
расширения → стоимость CPU/GPU/памяти → проверка поведения. Если для локальной функции требуется
изменение другого существующего модуля вне согласованной области, обсудить это до редактирования.
После изменения сопоставить план с фактическим diff и перечислить новые связи или их отсутствие.

Рефакторинг 10.11.2026 сохраняет публичные имена типов, форматы конфигурации/Dock/capture,
число слотов, порядок систем/проходов и изображение. Проверки ABI дополнены alignment/offsetof.
ECS-запросы кэшируются до структурной мутации, ограниченные журналы используют кольцевое хранение;
снимки массивов остаются независимыми значениями. Замеры — [PERFORMANCE.md](PERFORMANCE.md).

Проверка рефакторинга: 32 теста с Metal API Validation, Debug/Release arm64, проверка графа и формата.
Дополнены сценарии invalidation запросов, wraparound/frozen snapshots, регистрации команд,
подключения pass-owned буфера, роста object buffer до 600 объектов и повторной подготовки после ошибки.
В Sandbox вручную проверены сцена, разделитель Dock, Profiler в отдельном окне и возврат,
захват Forward/Output с инспекцией ресурсов. Ошибка выделения GPU-памяти искусственно не вызывалась;
порядок обновления ёмкости после успешного allocation проверен просмотром кода.
